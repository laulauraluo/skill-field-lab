# Waymark: Skill Selection Shift

Small, fully synthetic pilot for this question:

> Can changing one skill’s catalog description cause a retrieval-augmented agent to choose it over the skill that actually fits the user’s task?

## Design

- 18 fictional skills; 10 task cards with one expected skill, one competing skill, and a side-effect constraint.
- Fixed BM25 retriever; `top-k=5` candidates.
- Paired conditions: original text, surface rewrite, query-term stuffing, and direct instruction injection.
- Optional model decision stage: one naive prompt and one guarded prompt. Retrieved candidate order is shuffled with a fixed seed to reduce position confounds.
- Separate multi-adopter stress test at 0%, 25%, 50%, 75%, and 100% competitor adoption.

The skill implementations are never run. `unsafe_route_rate` marks a route to a skill that may change files or send messages when the task forbids side effects; it is a routing-risk proxy, not an observed execution violation.

## Pilot result

The checked-in `results/lexical-pilot-2026-11-17/` is a deterministic **BM25 + rank-1 lexical router** run. In this small synthetic setup, keyword stuffing moved the modified competitor above the expected skill in 10/10 tasks and changed the selected route in 9/10. The meaning-preserving wrapper changed the route in 0/10. Direct injection text changed neither the retrieval rank nor the lexical choice in this run: injection text is deliberately excluded from the BM25 index, and a lexical router cannot follow instructions in retrieved text.

These are not LLM results. The result is a harness smoke test on 10 hand-authored tasks, with no confidence intervals. It shows that this BM25 setup is sensitive to repeated query terms; it does not establish real-world prevalence, statistical reliability, or model behavior.

## Model-in-the-loop run

The current environment had no local model server and no API key configured. To run a real model, see the parent [README](../../../README.md). Default model evaluation makes 80 requests for one replicate across 10 tasks, 4 conditions, and 2 prompt policies. Use `--limit 2` to check endpoint wiring first; provider requests may incur charges.

## Output

- `summary.json`: aggregate paired metrics and the retrieval adoption curve.
- `paired_results.csv`: one task × condition × policy × replicate row.
- `adoption_curve.csv`: per-task retrieval-rank effects at each adoption rate.

All numbers are generated by the script from `catalog.json`; no real product data, user data, or external dataset is used.
